# Final-result POSITION() design contract

GitHub issue #150 introduces `POSITION()` as a deferred, one-based result-sequence value. It is evaluated after ordering and DISTINCT but before OFFSET and LIMIT, including grouped results. Explicit set-operation projections remain rejected pending composition-aware execution support.

`POSITION()` belongs to the completed logical sequence after WHERE, grouping, HAVING, set operations, DISTINCT and final ORDER BY, but before OFFSET and LIMIT. For an ordered query with `LIMIT 10 OFFSET 100`, returned positions start at 101. With no deterministic final ORDER BY, positions reflect the observed execution order without promising repeatability; ties remain unspecified unless the ordering breaks them. The function does not impose a hidden sort or tie-breaker.

The initial placement contract permits only a standalone SELECT projection such as `SELECT POSITION() AS position, id FROM @source ORDER BY id`. It rejects use inside other scalar expressions, predicates, grouping keys and ORDER BY expressions. ORDER BY dependencies on POSITION aliases are rejected to avoid circular ordering. Explicit compound-result projection placement remains unsupported and is rejected rather than silently assigning incorrect positions; nested query scopes require additional conformance coverage. DISTINCT must operate on the underlying values before the deferred position is attached, so POSITION cannot make otherwise identical rows distinct.

`POSITION()` is distinct from future window functions. Window expressions will have independent partition and ordering semantics; both features may share staged expression evaluation and row-context plumbing, but POSITION must not be implemented by injecting an implicit `ROW_NUMBER() OVER (...)`.

The planner classifies POSITION() as a final-result expression without metadata requirements and conservatively disables source-prefix early LIMIT termination until that optimisation is certified for deferred numbering. This safety barrier may sacrifice an optimisation but does not change result semantics.

Independent conformance oracles cover paginated and DISTINCT final positions, optimiser differential cases, deterministic invalid-compound diagnostics, and a POSITION projection within the maximal parser torture query. Explicit UNION operands are rejected before the resolver splits them into separate query bodies. Nested CTE and derived-relation execution tests establish that each query block numbers its own ordered sequence, with an enclosing query free to reorder those already numbered rows. The current project uses the hand-written parser and a parser-neutral EBNF contract; a runnable Lark parser is not present in this tree, so implementation-level Lark parity remains a future integration requirement rather than a tested claim. Final-position projections on explicit compound results remain unsupported. The general explain presentation does not yet expose a dedicated final-position operator.
